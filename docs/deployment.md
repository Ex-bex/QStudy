# Публичный запуск QStudy

Для доступа из интернета подготовлена схема **Linux-сервер → Caddy с HTTPS → Next.js → FastAPI**. Все функции используют настоящую базу и API; статическая публикация одного интерфейса не заменяет этот запуск. Cloudflare не используется.

На момент подготовки этой инструкции сервер и домен ещё не выбраны: действительного публичного адреса проекта пока нет. Ниже приведены действия для владельца нового хоста. `qstudy.example.org`, `owner@example.org`, `SERVER_IP` и имена пользователей — примеры; замените их своими значениями. Примерный домен не принадлежит проекту и не предназначен для запуска.

## Выбор сервера и домена

Для первого постоянного хоста рекомендована **Ubuntu 24.04 LTS, x86_64, 2 vCPU, 4 ГБ RAM, от 40 ГБ диска и публичный IPv4**. Это стартовый размер для небольшой учебной платформы, а не подтверждённый предел количества студентов. Место потребуется также образам, пользовательским загрузкам и копиям; рост нагрузки и данных требует наблюдения и увеличения ресурсов.

Варианты, проверенные по официальным страницам 11 октября 2026 года:

Цена, налоги, доступность локации и способы оплаты могут измениться. Домен оплачивается отдельно; выбирайте доступное вам имя, не предполагая, что конкретный домен QStudy свободен. Для загрузок и резервных копий могут потребоваться дополнительные диски или внешнее хранилище. VPS и домен владелец приобретает в своём аккаунте.

Можно разместить сайт на постоянно включённом собственном компьютере, но потребуется публичный адрес провайдера, настройка маршрутизатора и входящие 80/443. При CGNAT обычный проброс портов не создаст внешний доступ. Переносимая Windows-команда `Start-QStudy-LAN.cmd` открывает только доверенную локальную сеть; публичный запуск в этой инструкции подготовлен для отдельного Linux-хоста.

Для Windows подготовлен отдельный production-менеджер `Manage-QStudy-Internet.cmd`, использующий эту же схему Docker/Caddy. Домашний компьютер можно настроить без аренды VPS: см. [инструкцию домашнего хостинга](home-hosting.md) с диагностикой CGNAT, DuckDNS, пробросом портов и автозапуском.

## До установки

1. Создайте Linux-сервер и запишите его публичный IP. Подключитесь по SSH с учётной записью, имеющей `sudo`. Закрытый SSH-ключ держите у себя; не вставляйте его в репозиторий или чат.
2. В DNS-панели домена создайте запись `A` для нужного имени на публичный IPv4 сервера. `AAAA` добавляйте только при действительно доступном IPv6; неправильная IPv6-запись может помешать проверке сертификата.
3. В сетевых правилах провайдера разрешите TCP 80 и 443. UDP 443 необязателен и используется для HTTP/3. SSH разрешите только из нужных вам адресов. Не открывайте 3000 и 8000 наружу.
4. Настройте системные сетевые правила с учётом Docker. Скрипт не открывает firewall автоматически; публикация Docker-портов имеет особенности относительно UFW. [Документация Docker](https://docs.docker.com/engine/install/ubuntu/#firewall-limitations).
5. Если переносите текущую установку, создайте готовую резервную копию в админке и сохраните отдельную защищённую копию `backend/.env`. Пользовательские данные не поступают на сервер из Git.

После обновления DNS проверяйте, что имя разрешается именно в IP выбранного сервера:

```bash
getent ahostsv4 qstudy.example.org
```

Изменения DNS могут распространяться не сразу. Проверка внутри сервера не заменяет пробу с другой сети, например мобильного интернета.

На Hetzner для существующей настройки Gmail используйте STARTTLS на порту 587: [он не заблокирован](https://docs.hetzner.com/cloud/servers/faq/#why-can-i-not-send-any-mails-from-my-server). У другого провайдера заранее проверьте исходящий доступ к SMTP 587. Размер сервера подходит для старта QStudy по оценке устройства приложения; нагрузочное тестирование большой группы пользователей ещё не проводилось.

## Получение исходников из закрытого GitHub

Репозиторий `Ex-bex/QStudy` остаётся закрытым даже после открытия сайта студентам. Выдайте серверу доступ только к чтению исходников; для простого одиночного хоста можно использовать отдельный deploy key. [Инструкция GitHub](https://docs.github.com/en/authentication/connecting-to-github-with-ssh/managing-deploy-keys).

На сервере установите Git и создайте ключ, если его ещё нет:

```bash
sudo apt-get update
sudo apt-get install -y git ca-certificates
ssh-keygen -t ed25519 -C "qstudy-host"
```

Запомните выбранный путь. Если оставили стандартный, публичная часть — `~/.ssh/id_ed25519.pub`; файл без `.pub` — закрытый ключ, его не публикуйте. Добавьте **публичную** часть через GitHub → репозиторий → Settings → Deploy keys → Add deploy key, без `Allow write access`. При первом SSH-соединении проверьте ключ сервера GitHub, не отключайте проверку известного хоста.

Создайте папку и получите основную ветку:

```bash
sudo install -d -m 755 -o "$USER" -g "$(id -gn)" /opt/qstudy
git clone --branch main git@github.com:Ex-bex/QStudy.git /opt/qstudy
cd /opt/qstudy
```

Если предпочитаете перенос архива исходников, убедитесь, что сохранены `frontend/`, `backend/app/`, lockfile, `deployment/` и `scripts/production/`. Не используйте публичный файловый обменник для архива с базой или рабочими секретами.

## Автоматическая подготовка и первый запуск

Все команды ниже выполняются на сервере из `/opt/qstudy`.

### Установка среды

```bash
sudo bash scripts/production/Install-Docker.sh
```

Установщик поддерживает Ubuntu 22.04, 24.04 и 26.04 LTS. Он проверяет существующие Docker/Compose, использует официальный APT-репозиторий Docker, устанавливает недостающее и включает Docker после перезагрузки. Чужие контейнеры и конфликтующие установленные среды не удаляются автоматически: при конфликте нужно сначала разобраться с существующими сервисами. [Официальная установка Docker](https://docs.docker.com/engine/install/ubuntu/).

Python, Node.js, библиотеки приложения и OCR устанавливаются в образы при сборке. Устанавливать эти среды вручную на host для работы приложения не требуется.

### Конфигурация

```bash
sudo bash scripts/production/Manage-QStudy.sh init qstudy.example.org owner@example.org
sudoedit deployment/.env
```

`init` создаёт закрытый файл `deployment/.env`, отдельные случайные `SECRET_KEY` и `BFF_PROXY_SECRET`, папки данных и корректные права. Повторный `init` с тем же доменом сохраняет существующий файл и секреты. Email здесь нужен для связи по сертификату; он не создаёт пользовательский аккаунт и не становится автоматически публичным контактом разработчика.

В редакторе настройте:

- `QSTUDY_DOMAIN` — настоящий домен, без `https://` и пути;
- `PUBLIC_BASE_URL` — ровно `https://` и этот домен, без завершающего `/`;
- `ACME_EMAIL` — действующий контакт для сертификата;
- `GEMINI_API_KEY` и доступную вашему ключу модель;
- `REGISTRATION_ENABLED='false'` на время первичной настройки или переноса; включить регистрацию можно после проверки администратора;
- SMTP и `RECOVERY_DELIVERY='smtp'` для самостоятельного восстановления по почте. Пока почта не настроена, допустим `disabled`; локальная выдача ссылок для публичного сервера не используется.

Пример SMTP-полей с вымышленными значениями:

```dotenv
RECOVERY_DELIVERY='smtp'
SMTP_HOST='smtp.gmail.com'
SMTP_PORT='587'
SMTP_SECURITY='starttls'
SMTP_USERNAME='your_email@gmail.com'
SMTP_PASSWORD='your_google_app_password'
SMTP_FROM='QStudy <your_email@gmail.com>'
```

Для Gmail нужен пароль приложения, а не основной пароль аккаунта: [подробная настройка](mail.md). Значения в production-файле записывайте в одинарных кавычках по образцу; символ `$` в пароле тогда не разворачивается Docker Compose. Не исполняйте `.env` командой `source` и не показывайте раскрытую конфигурацию через `docker compose config`: она содержит секреты. Штатная проверка использует режим без печати значений.

### Проверка и запуск

```bash
sudo bash scripts/production/Manage-QStudy.sh check
sudo bash scripts/production/Manage-QStudy.sh start
```

`check` проверяет конфигурацию, закрытые права, публичное DNS-разрешение, Docker и Compose. Он не доказывает, что домен указывает именно на выбранный сервер или что входящие порты доступны снаружи: эти условия проверьте отдельно.

`start` собирает производственный frontend и backend с зафиксированными зависимостями, проверяет Caddy и, если выбран SMTP, соединение с почтой, TLS и вход. Эта проверка письма не отправляет. Затем запускает здоровые контейнеры. Caddy получает и продлевает HTTPS-сертификат при подходящей настройке домена и доступных портах. [Автоматический HTTPS Caddy](https://caddyserver.com/docs/automatic-https).

Затем команда проверяет настоящий HTTPS-адрес, `/api/health` и заголовок HTTPS-защиты. Успех выводит `public_https_verified` и действительный URL. Если контейнеры запущены, но эта проверка не прошла, сайт ещё нельзя считать подтверждённо опубликованным. Разберите сообщение, DNS и сетевые правила; не отключайте проверку TLS для обхода ошибки.

### Первый администратор

Для **новой пустой базы** создайте администратора после успешного запуска:

```bash
sudo bash scripts/production/Manage-QStudy.sh admin admin@example.org --name 'Администратор'
```

Команда внутри backend запускает `app.bootstrap_admin` и дважды скрыто спрашивает пароль. В командной строке пароль не указывается. Нужны 10–128 символов, минимум буква и цифра. Если указанный email уже есть, команда назначает административную роль, **меняет его пароль** и отзывает прежние сессии. Для обычного назначения группы и роли дальше используйте админку.

Регистрация никогда не создаёт администратора автоматически. При переносе существующей базы действующий административный аккаунт переносится вместе с ней; повторно запускать `admin` для него не требуется, если вы не хотите сменить пароль.

В свежей установке отсутствуют личные документы, аккаунты и база прежнего компьютера. Однократный импорт проверенных локальных учебных оригиналов требует этих оригиналов; Docker-образ специально не включает `local-documents/`. Для сохранения действующих групп, расписания, планов и личных данных используйте перенос копии ниже либо заполните новую установку в админке.

## Перенос действующей базы с Windows

1. В текущей админке создайте резервную копию и скачайте готовый ZIP. Он содержит согласованную базу и загрузки, включая загруженные логотипы. При переходе на новый основной хост завершите изменения на старом и остановите его, чтобы записи после выбранной копии не остались только там.
2. Подготовьте сервер и выполните первый `start` с временно закрытой регистрацией. Новая база будет заменена старой при восстановлении; не начинайте работать со свежими аккаунтами в промежутке.
3. Перенесите архив через защищённое SSH-соединение. Пример в PowerShell на старом компьютере:

```powershell
scp 'C:\Backups\qstudy-20261011-120000-abcd1234.zip' deploy@SERVER_IP:~/
```

4. На сервере поместите **тот же архив с его штатным именем** в приватную папку и восстановите права:

```bash
cd /opt/qstudy
sudo install -m 600 -o 10001 -g 10001 "$HOME/qstudy-20261011-120000-abcd1234.zip" deployment/data/backups/
sudo bash scripts/production/Manage-QStudy.sh permissions
sudo bash scripts/production/Manage-QStudy.sh verify qstudy-20261011-120000-abcd1234.zip
sudo bash scripts/production/Manage-QStudy.sh restore qstudy-20261011-120000-abcd1234.zip
```

Подставляйте действительное имя скачанного файла. `verify` и `restore` принимают **только имя** готового архива в `deployment/data/backups/`, а не произвольный путь. Проверяются структура архива, контрольные суммы и целостность SQLite. Не распаковывайте ZIP поверх работающих данных вручную.

`restore` останавливает сервисы, сохраняет текущее состояние перед заменой, восстанавливает согласованные базу и загрузки, затем запускает приложение и проверяет HTTPS. Старые сессии и ссылки восстановления отзываются; незавершённые задания ИИ возвращаются в очередь. При ошибке восстановления сервисы остаются остановлены, чтобы не принять неправильные данные; предыдущее состояние сохранено либо откатилось. Прочитайте ошибку и проверьте архив до повторного запуска.

5. Перенесите значения SMTP и ИИ из закрытого Windows-файла в `deployment/.env` через приватный редактор. Сам архив не содержит `.env`. Сохраните новый серверный `PUBLIC_BASE_URL`, отдельные созданные секреты и контейнерные пути; не копируйте Windows-файл целиком поверх production-конфигурации.
6. Если изменили настройки после запуска, выполните `start` снова: контейнеры получают новые параметры. Войдите прежним аккаунтом на HTTPS-сайте, проверьте группу, заметки, файлы, логотипы и состояние очереди. Пароль из перенесённой базы остаётся прежним, если его отдельно не меняли.
7. Локальные исходники из `local-documents/` и другие файлы, не вошедшие в штатную копию, сохраните отдельно. Для обычной работы с уже перенесённым планом их не надо публиковать в web-папке; новые документы загружайте через интерфейс.

## Проверка работы после публикации

Проверьте с другого устройства и другой сети:

1. HTTPS-домен открывается без предупреждения о сертификате, HTTP перенаправляется на HTTPS.
2. `/api/health` отвечает данными сервиса QStudy, главная страница и «Связь с разработчиками» открываются.
3. Администратор входит и назначает тестовому студенту группу; студент видит план и может работать со своими заметками. Общие изменения доступны только администратору.
4. Собственный запрос восстановления приходит по SMTP с именем отправителя QStudy и ссылкой на **этот HTTPS-домен**, а не `127.0.0.1`.
5. ИИ создаёт результат с действующим ключом; PDF-скан проходит OCR, а статус импорта сохраняется при обновлении страницы.
6. В админке создаётся и скачивается копия; обычный перезапуск сохраняет базу, файлы и задания ИИ.

После проверки при необходимости включите `REGISTRATION_ENABLED='true'` в `deployment/.env` и примените конфигурацию через `start`. Пароли тестовых пользователей не используйте для постоянных аккаунтов.

## Ежедневное управление

| Задача | Команда из `/opt/qstudy` |
| --- | --- |
| Посмотреть состояние | `sudo bash scripts/production/Manage-QStudy.sh status` |
| Проверить конфигурацию без обращения к DNS | `sudo bash scripts/production/Manage-QStudy.sh check --offline` |
| Запустить или применить настройки | `sudo bash scripts/production/Manage-QStudy.sh start` |
| Остановить сайт, сохранив данные | `sudo bash scripts/production/Manage-QStudy.sh stop` |
| Создать копию вручную | `sudo bash scripts/production/Manage-QStudy.sh backup` |
| Проверить SMTP без отправки письма | `sudo bash scripts/production/Manage-QStudy.sh mail-check` |
| Проверить архив | `sudo bash scripts/production/Manage-QStudy.sh verify ИМЯ_АРХИВА.zip` |
| Восстановить архив | `sudo bash scripts/production/Manage-QStudy.sh restore ИМЯ_АРХИВА.zip` |
| Восстановить права после переноса файлов | `sudo bash scripts/production/Manage-QStudy.sh permissions` |

Автоматические копии включены: по умолчанию каждые 24 часа работающего сервера, последние 14 готовых архивов; есть копия перед обновлением структуры базы. Файлы находятся в `deployment/data/backups/`. Скачивайте готовые копии через админку и держите дополнительную копию вне диска сервера. `.env` и закрытый SSH-ключ сохраняйте отдельно защищённым способом.

Контейнеры настроены `restart: unless-stopped`, Docker запускается как служба. После перезагрузки host работающие до неё контейнеры поднимаются снова; намеренно остановленные командой `stop` нужно явно запустить. В очереди ИИ возможна пауза до окончания прежней блокировки, но её записи сохраняются.

### Обновление кода

```bash
cd /opt/qstudy
git status --short
git pull --ff-only origin main
sudo bash scripts/production/Manage-QStudy.sh update
```

Сначала сохраните собственные исходные правки и получите проверенный commit. `update` создаёт копию существующего backend, собирает новые образы до замены контейнеров, не удаляет постоянные данные и выполняет публичную проверку. При ошибке сборки изучите сообщение до повторного запуска; при ошибке запуска может понадобиться возврат к предыдущему проверенному коду и, если менялась схема, соответствующей копии.

Git-обновление само по себе не пересобирает сайт. Пользовательские данные и `deployment/.env` в Git не отправляются. Не выполняйте `docker compose down -v`, удаление `deployment/data/` или принудительный сброс Git ради обычного обновления.

### Где находятся данные

| Место | Содержимое |
| --- | --- |
| `deployment/.env` | Закрытые настройки и секреты, права 600 |
| `deployment/data/backend/studyhub.db` | Постоянная SQLite-база: аккаунты, учебный план, очередь и логотипы |
| `deployment/data/backend/uploads/` | Приватные загруженные файлы |
| `deployment/data/backups/` | Готовые архивы и сохранённое состояние перед восстановлением |
| Docker-тома `caddy_data`, `caddy_config` проекта | Сертификаты и состояние Caddy; не удаляйте их при обычном обновлении |

Backend выполняется одним процессом, а SQLite, очередь и планировщик принадлежат этой установке. Не увеличивайте число backend-реплик с общим файлом SQLite: распределённое развёртывание требует отдельной подготовки базы, файлов и ограничителей запросов.

## Диагностика

Состояние смотрите штатной командой. Для последних журналов конкретного сервиса:

```bash
sudo docker compose --project-directory deployment --env-file deployment/.env -f deployment/compose.yml logs --tail 80 caddy
sudo docker compose --project-directory deployment --env-file deployment/.env -f deployment/compose.yml logs --tail 80 frontend
sudo docker compose --project-directory deployment --env-file deployment/.env -f deployment/compose.yml logs --tail 80 backend
```

Журналы Docker ограничены по размеру. Перед передачей ошибки удалите любые личные данные; файл `.env`, письма со ссылкой восстановления и закрытые ключи не прикладывайте.

| Ошибка | Что проверить |
| --- | --- |
| Установщик обнаружил другой Docker/containerd | Существующие сервисы и [официальные требования](https://docs.docker.com/engine/install/ubuntu/); установщик ничего не удаляет за вас |
| `check` не видит домен | Запись A/AAAA, публичный IP и время распространения DNS |
| Контейнеры готовы, но нет `public_https_verified` | DNS должен указывать на этот host; TCP80/443 должны доходить до Caddy, не быть заняты другим web-сервером; проверьте журнал Caddy |
| Вход или запись возвращает 403 | Открывайте настоящий HTTPS-домен, проверьте равенство `PUBLIC_BASE_URL` и домена. Не открывайте внутренний порт frontend в обход Caddy |
| Ошибка прав базы/загрузок | Выполните `permissions`; данные должны принадлежать UID/GID10001, не используйте chmod777 |
| SMTP не отправляет | Правильный режим, TLS/порт, пароль приложения, ограничения исходящих SMTP-портов у провайдера и спам; после настройки примените `start` |
| ИИ недоступен | Ключ, доступная модель, квота и исходящее соединение сервера |
| Нет текста в PDF | Читаемость и размер документа, предупреждение OCR; Linux-образ содержит Tesseract с русским, английским и казахским языками |
| Сайт не работает после заполнения диска | Свободное место для базы, загрузок, образов и копий; сохраните нужные архивы вне host перед очисткой |
| Не прошёл restore | Правильный штатный архив и его basename, проверка SHA-256 и SQLite, права и свободное место. Не запускайте случайную распаковку поверх базы |

Полное использование и самостоятельные изменения описаны в [user-guide.md](user-guide.md) и [customization.md](customization.md).
