# Передача QStudy другу: Windows и собственный домен

Эта инструкция предназначена владельцу компьютера, который будет постоянно обслуживать QStudy. Схема: **интернет → роутер друга → Caddy с HTTPS → QStudy в Docker**. Cloudflare, исходящий туннель и аренда VPS не требуются. Нужны публичный IPv4 без CGNAT, разрешённые входящие TCP 80/443, доступ к настройкам роутера и собственному DNS-домену.

Подготовка файлов сама по себе не публикует сайт. Сначала получите исходники, заполните закрытые настройки, соберите приложение и восстановите данные без внешнего входа. Затем настройте сеть и запустите HTTPS-прокси. Доступность подтверждается с телефона через мобильный интернет; до этой проверки не раздавайте адрес студентам.

Ниже `qstudy.example.org`, `owner@example.org`, `your-admin@example.org`, `192.168.1.50` и имя ZIP — вымышленные значения. Настоящие адреса и секреты задавайте **на компьютере друга**, не в Git. Все команды PowerShell выполняются из корня проекта, например `C:\QStudy`.

## 1. Подтвердите условия подключения

Друг должен уточнить у своего провайдера:

> На компьютере будет веб-сайт. Нужен публичный IPv4 без CGNAT с разрешёнными входящими TCP 80 и 443. Адрес статический или динамический? Разрешает ли договор домашний сервер? Кто может настроить проброс портов на вашем роутере?

«Белый» адрес не обязательно статический. Сравните **WAN / Internet IPv4** в панели роутера с результатом диагностики на хосте:

```powershell
Set-Location 'C:\QStudy'
.\Test-QStudy-HomeNetwork.cmd
```

Для передачи известного WAN можно запустить:

```powershell
.\Test-QStudy-HomeNetwork.cmd -RouterWanIPv4 'PUBLIC_IPV4' -Domain 'qstudy.example.org'
```

Вместо `PUBLIC_IPV4` укажите фактический адрес из роутера. Один внешний адрес, который сообщает диагностический сервис, не доказывает отсутствие CGNAT: важно сопоставить его с WAN. Приватный WAN `10.*`, `172.16.*–172.31.*`, `192.168.*` или диапазон `100.64.*–100.127.*` означает промежуточную сеть; выясните причину у провайдера. При двух собственных роутерах требуется согласованный проброс на обоих. [Разъяснение TP-Link](https://www.tp-link.com/ph/support/faq/785/), [диапазон CGNAT](https://www.rfc-editor.org/info/rfc6598/).

Если провайдер изменил пароль панели, попросите его предоставить клиентский доступ либо настроить проброс. Не сбрасывайте устройство без согласования: можно потерять параметры интернет-подключения. Для прямого хостинга настройка роутера необходима, но **удалённое управление роутером из интернета включать не нужно**. [Рекомендации TP-Link для оборудования провайдера](https://www.tp-link.com/us/support/faq/4370/).

## 2. Подготовьте Windows и Docker

Рекомендуется поддерживаемая 64-битная Windows 11 с обновлениями. Если используется Windows 10, проверьте, что её редакция и версия всё ещё обслуживаются Microsoft и подходят текущему Docker Desktop. Docker поддерживает только обслуживаемые версии Windows; перечень и требования проверяйте перед установкой. Нужны аппаратная виртуализация, WSL 2 версии 2.1.5 или новее и минимум 8 ГБ RAM. Для сборки и OCR удобнее 16 ГБ. [Официальные требования Docker Desktop](https://docs.docker.com/desktop/setup/install/windows-install/).

1. Подключите компьютер к роутеру кабелем Ethernet, если возможно. Обеспечьте свободное место для образов, базы, документов и резервных копий.
2. Если WSL отсутствует, в PowerShell от имени администратора выполните команды ниже. После требуемой перезагрузки войдите в тот же Windows-аккаунт.

```powershell
wsl --install --no-distribution
wsl --update
```

Отдельная Ubuntu внутри WSL для этой схемы не нужна: Docker Desktop использует собственную Linux-среду. [Команды WSL](https://learn.microsoft.com/en-us/windows/wsl/basic-commands).

3. Установите [Docker Desktop](https://docs.docker.com/desktop/setup/install/windows-install/), откройте его, самостоятельно примите условия и используйте **Linux containers / WSL 2**. Дождитесь работы Docker Engine.
4. Проверьте в PowerShell:

```powershell
docker version
docker compose version
```

У `docker version` должны отображаться Client **и Server**. Наличие только программы Docker без запущенного Engine недостаточно.

Node.js, Python приложения, библиотеки и Tesseract OCR устанавливаются внутри контейнеров при сборке. Не нужно вручную устанавливать пакеты приложения в Windows. Мастер подготовки проверяет доступность среды; установка компонентов Windows или первый запуск Docker могут потребовать действий владельца и перезагрузки.

## 3. Получите исходники из закрытого GitHub

Репозиторий [Ex-bex/QStudy](https://github.com/Ex-bex/QStudy) остаётся приватным. Открытие сайта посетителям не требует открытия исходников.

Можно передать другу архив **только исходников** или предоставить хосту доступ к чтению Git. Для отдельного серверного компьютера подходит deploy key без `Allow write access`. Закрытый ключ хранится на хосте, владелец репозитория добавляет в GitHub только публичную часть. Не передавайте другу пароль вашего GitHub и не вставляйте токен в URL клонирования. [Настройка deploy key](https://docs.github.com/en/authentication/connecting-to-github-with-ssh/managing-deploy-keys).

После настройки Git/SSH и проверки ключа сервера GitHub:

```powershell
git clone --branch main git@github.com:Ex-bex/QStudy.git 'C:\QStudy'
Set-Location 'C:\QStudy'
```

Не перезаписывайте существующую папку с данными ради повторного клонирования. Архив исходников не должен включать `.env`, `.local`, SQLite-базу, загрузки, резервные копии, `.venv`, `node_modules` и `.next`. Эти рабочие данные не приходят из Git; нужную копию передают отдельно.

## 4. Запустите мастер подготовки без публикации

```powershell
Set-Location 'C:\QStudy'
.\Setup-QStudy-Host.cmd -Domain 'qstudy.example.org' -Email 'owner@example.org'
```

Мастер помогает подготовить production-конфигурацию и проверить условия запуска. По умолчанию он **не запускает публичный сайт** и не открывает порты. Параметр `-Email` здесь относится к связи по HTTPS-сертификату, а не к назначению администратора. Настройки роутера и DNS владелец выполняет в своих панелях.

Укажите SMTP и ключ ИИ в приватных запросах мастера либо в редакторе `deployment/.env`. Настройки публичной установки отдельны от прежнего `backend/.env`.

| Поле | Значение на новом компьютере |
| --- | --- |
| `QSTUDY_DOMAIN` | Реальное имя сайта без `https://` и пути |
| `PUBLIC_BASE_URL` | Ровно `https://` и то же имя, без завершающего `/` |
| `ACME_EMAIL` | Контакт для сертификата |
| `REGISTRATION_ENABLED` | `false` до завершения первоначальной проверки |
| `GEMINI_API_KEY`, `GEMINI_MODEL` | Рабочий ключ и доступная ему модель |
| `RECOVERY_DELIVERY` | `smtp`, если почта настроена; иначе `disabled` |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURITY` | Сервер, порт и TLS-режим вашей почты |
| `SMTP_USERNAME`, `SMTP_PASSWORD`, `SMTP_FROM` | Учётная запись, закрытый пароль и отправитель QStudy |

Для Gmail используйте пароль приложения, SMTP `smtp.gmail.com`, порт `587`, режим `starttls`; отправителем может быть `QStudy <your_email@gmail.com>`. [Подробная настройка почты](mail.md). Обычный пароль Google не подставляйте вместо пароля приложения. Проверьте разрешённое исходящее соединение SMTP у провайдера.

При ручном редактировании используйте одинарные кавычки по production-шаблону. Не запускайте `.env` как PowerShell-скрипт и не печатайте `docker compose config`: раскрытая конфигурация содержит секреты. Случайные `SECRET_KEY` и `BFF_PROXY_SECRET`, созданные подготовкой, сохраните; не заменяйте production-файл целиком прежним Windows `.env`. Контейнерные пути и новый публичный URL должны остаться корректными.

Для повторной проверки без обращения к DNS:

```powershell
.\Manage-QStudy-Internet.cmd check -Offline
```

Если DNS или Docker ещё не готовы, исправьте указанные условия и повторите проверку. Не отключайте проверку HTTPS или защиту входа, чтобы обойти ошибку.

## 5. Соберите приложение и подготовьте данные без публикации

До настройки проброса портов выполните:

```powershell
.\Manage-QStudy-Internet.cmd prepare
```

Эта команда собирает production-образы и проверяет Caddy, но запускает только backend/frontend во внутренней сети Docker. Caddy и внешние порты не запускаются; готовое публичное DNS ещё не требуется. Если Caddy этого проекта уже работает, подготовка откажется продолжать: сначала остановите приложение штатной командой `stop`, чтобы не смешать частную подготовку с действующим сайтом.

### Перенос существующей базы

Если нужно сохранить аккаунты, группу, расписание, силабусы, заметки, загруженные логотипы и задания ИИ:

1. На старом компьютере в админке создайте **готовую штатную резервную копию** и скачайте ZIP. Архив содержит согласованную базу и загрузки. Пароли аккаунтов остаются в виде хешей; это всё равно приватные пользовательские данные.
2. Перед финальной копией завершите изменения на старом хосте и остановите его. После переключения пользователи должны работать только с новым хостом, иначе записи разойдутся.
3. Передайте ZIP другу через защищённый канал или лично на защищённом носителе. Не добавляйте архив в GitHub, публичный обменник или папку сайта.
4. Сохраните на новом хосте исходное имя ZIP и поместите его в `C:\QStudy\deployment\data\backups\` до проброса портов и публикации. Укажите настоящее имя в командах:

```powershell
.\Manage-QStudy-Internet.cmd verify -Archive 'qstudy-20261011-120000-abcd1234.zip'
.\Manage-QStudy-Internet.cmd restore -Archive 'qstudy-20261011-120000-abcd1234.zip' -NoPublish
```

`verify` проверяет структуру, контрольные суммы и целостность SQLite. `restore -NoPublish` останавливает сервисы, сохраняет прежнее состояние и восстанавливает базу вместе с файлами, затем поднимает только внутренние backend/frontend. Caddy остаётся остановлен; сайт не публикуется и внешняя HTTPS-проба не выполняется. Команды принимают только имя готового архива из `deployment/data/backups/`, не произвольный путь. При ошибке восстановления сервисы остаются остановлены — разберите сообщение, а не запускайте ручную распаковку поверх базы.

5. SMTP и ключ ИИ настройте отдельно. Архив не содержит `.env`; секреты передавайте приватно или введите новые ключи владельца хоста.

Не копируйте только `studyhub.db` без загрузок и не распаковывайте ZIP поверх работающей базы. Приватные исходные документы из `local-documents/`, которых нет в штатной копии, при необходимости передайте отдельно; они не должны стать публичными файлами сайта.

Администратор переносится с существующей базой. Его пароль остаётся прежним, старые сессии и ссылки восстановления отзываются, незавершённые задания ИИ возвращаются в очередь. Не начинайте работу с временными свежими аккаунтами до восстановления.

### Новая установка без переноса

После `prepare` создайте первого администратора:

```powershell
.\Manage-QStudy-Internet.cmd admin -Email 'your-admin@example.org' -Name 'Администратор'
```

Пароль вводится дважды скрыто, без аргумента командной строки. Если email уже существует, команда назначает административную роль, **меняет пароль и отзывает сессии**. После переноса базы выполнять её для прежнего администратора не нужно, если смена пароля не требуется. `-Email` сертификата в мастере не создаёт аккаунт автоматически.

Пока работают только внутренние сервисы, вход через браузер ещё не опубликован. Первую браузерную проверку выполните после HTTPS-запуска в разделе 8.

## 6. Закрепите LAN-адрес и настройте домен

На компьютере посмотрите активный Ethernet/Wi-Fi:

```powershell
Get-NetIPConfiguration
```

В роутере создайте **DHCP reservation / Статическую аренду** для его сетевой карты, например `192.168.1.50`. Для проброса нужен LAN-адрес Windows-компьютера, не адрес WSL/Docker/VPN.

В DNS-панели своего домена:

| Запись | Настройка |
| --- | --- |
| `A` для выбранного имени, например `qstudy` | Публичный IPv4 подключения друга |
| `AAAA` | Не добавлять, пока входящий IPv6 не настроен и не проверен |
| Второе имя, например `www` | Не требуется; сначала используйте одно имя, совпадающее с `PUBLIC_BASE_URL` |

Если выбран корень домена, настройте `A` для `@` по правилам DNS-провайдера. Ошибочная `AAAA` может направить посетителей и проверку сертификата на неработающий IPv6. [Условия автоматического HTTPS Caddy](https://caddyserver.com/docs/automatic-https).

При **статическом публичном IPv4** достаточно `A`; обновлять его при каждом запуске не нужно. При **динамическом** настройте DDNS через поддерживаемый клиент роутера или DNS API своего провайдера. Для поддомена можно использовать `CNAME` на собственное имя DuckDNS и штатный клиент QStudy из [домашней инструкции](home-hosting.md#обновление-duckdns). Это необязательный вариант: собственный домен не требует перехода на DuckDNS, если DNS-провайдер уже поддерживает безопасное автоматическое обновление. Для корня домена обычный `CNAME` часто неприменим — следуйте правилам своей DNS-панели.

DDNS должен получать адрес подключения хоста, а не VPN. Разовое изменение `A` не обеспечит постоянную доступность при смене IP. Токены DNS/регистратора нельзя хранить в Git. DDNS не открывает порты и не устраняет CGNAT.

Проверьте после распространения DNS:

```powershell
Resolve-DnsName 'qstudy.example.org' -Type A
.\Test-QStudy-HomeNetwork.cmd -Domain 'qstudy.example.org'
```

## 7. Откройте только вход сайта

До этого шага исходники и закрытая конфигурация уже должны находиться на хосте, данные должны быть восстановлены либо создан первый администратор. Регистрация пока закрыта.

В локальной панели роутера настройте **Port Forwarding / Virtual Servers**:

| Внешний порт | Протокол | Внутренний адрес | Внутренний порт |
| --- | --- | --- | --- |
| 80 | TCP | Закреплённый LAN-адрес хоста | 80 |
| 443 | TCP | Тот же адрес | 443 |

UDP 443 необязателен для HTTP/3. Для обычного HTTPS достаточно TCP. [Инструкция TP-Link по пробросу](https://www.tp-link.com/us/support/faq/1379/).

В Windows откройте `wf.msc` → **Правила для входящих подключений → Создать правило → Для порта**. Разрешите TCP `80,443` для действующего профиля домашней сети; назовите правило `QStudy HTTP HTTPS`. Профиль можно узнать через `Get-NetConnectionProfile`. Не выключайте брандмауэр целиком. Если используется другой антивирус или firewall, учтите его правила и работу `com.docker.backend.exe`. [Сеть Docker Desktop](https://docs.docker.com/desktop/features/networking/).

Не включайте DMZ, WAN-управление роутером и открытие всех портов. Не пробрасывайте `3000`, `8000`, Docker API или Windows RDP. Production frontend/backend доступны только внутри контейнеров; вход посетителей обслуживает Caddy. Если роутер использует внешние 80/443 для собственного управления, устраните этот конфликт согласно его инструкции.

## 8. Запустите production через HTTPS

После настройки DNS, роутера и firewall:

```powershell
.\Manage-QStudy-Internet.cmd check
.\Manage-QStudy-Internet.cmd start
```

Можно вместо этих двух действий повторно использовать мастер с явным запуском:

```powershell
.\Setup-QStudy-Host.cmd -Domain 'qstudy.example.org' -Email 'owner@example.org' -Start
```

Сборка ставит зафиксированные зависимости в образы, проверяет Caddy, а при выбранном SMTP — соединение, TLS и вход без отправки письма. Caddy получает и продлевает сертификат. Штатный запуск проверяет HTTPS, `/api/health` и защитный заголовок; успех обозначается `public_https_verified`. Если эта проверка не прошла, контейнеры могут остаться работающими для диагностики, но публикация ещё не подтверждена.

После завершённой частной подготовки войдите административным аккаунтом через HTTPS и проверьте группу и материалы. Если внешняя HTTPS-проба не прошла, исправьте DNS и сетевые правила; уже восстановленные данные повторно распаковывать не нужно.

## 9. Проверьте с мобильного интернета

На телефоне отключите Wi-Fi и VPN, используйте мобильный интернет. Откройте **настоящий HTTPS-домен**, затем проверьте:

1. Сайт открывается без предупреждения о сертификате; HTTP перенаправляется на HTTPS.
2. `/api/health` показывает сервис QStudy. Администратор входит; студент получает свою группу и не может изменять глобальные настройки.
3. На месте группа, расписание, силабусы, недели/модули, личные заметки, загруженные документы и логотипы.
4. Восстановление пароля отправляет письмо с именем QStudy и ссылкой на этот домен. Проверка `mail-check` проверяет подключение, но не заменяет получение настоящего письма.
5. ИИ работает с выбранным ключом, PDF-скан проходит OCR, а фоновые задания сохраняются после обычного перезапуска.
6. В админке создаётся и скачивается готовая резервная копия.

Проверка из той же Wi-Fi-сети недостаточна. Если внешний сайт работает, а дома тот же домен не открывается, настройте NAT loopback или локальное DNS-разрешение **того же имени** на LAN-адрес хоста. Не переходите на публичный HTTP и не выключайте проверку Origin/Host.

Только после проверки данных и администратора включите `REGISTRATION_ENABLED='true'`, если самостоятельная регистрация нужна, и примените настройки через `start`. Затем передайте студентам HTTPS-адрес. `localhost`, `127.0.0.1` и LAN-адрес не являются ссылкой на публичный сайт.

## 10. Включите автозапуск и обслуживание

В Docker Desktop включите **Settings → General → Start Docker Desktop when you sign in to your computer**. Затем:

```powershell
.\Manage-QStudy-Internet.cmd install-autostart
```

При использовании мастера эту задачу можно включить параметром `-EnableAutostart`. Не включайте её до завершения переноса и проверки рабочих настроек.

Автозапуск действует **после входа того же Windows-пользователя**, не до экрана входа. После отключения питания или обновления Windows кто-то должен войти, дождаться Docker и проверить сайт. Скрипты не отключают пароль Windows. В параметрах питания отключите сон при питании от сети; монитор может гаснуть. Закрытие крышки ноутбука также не должно усыплять хост при выбранном способе работы. Интернет, питание и свободный диск нужны постоянно. [Настройки Docker Desktop](https://docs.docker.com/desktop/settings-and-maintenance/settings/).

| Действие | Команда из корня проекта |
| --- | --- |
| Проверить контейнеры | `.\Manage-QStudy-Internet.cmd status` |
| Применить изменённый `.env` | `.\Manage-QStudy-Internet.cmd start` |
| Проверить SMTP без письма | `.\Manage-QStudy-Internet.cmd mail-check` |
| Создать копию | `.\Manage-QStudy-Internet.cmd backup` |
| Остановить сайт | `.\Manage-QStudy-Internet.cmd stop` |
| Отключить следующий автозапуск | `.\Manage-QStudy-Internet.cmd remove-autostart` |

При включённой задаче следующий вход снова запустит QStudy даже после `stop`. Для длительной остановки сначала выполните `remove-autostart`, затем `stop`.

Автоматические копии включены: по умолчанию каждые 24 часа работающего сервера сохраняются последние 14 готовых архивов. Они лежат на том же диске и не защищают от его поломки — регулярно сохраняйте дополнительную копию вне хоста. `.env` и закрытый Git-ключ храните отдельно защищённым способом. Проверку восстановления выполняйте на отдельной тестовой установке.

Постоянные данные находятся в `deployment/data/backend/`, копии — в `deployment/data/backups/`; сертификаты Caddy — в Docker volumes. Не удаляйте эти папки/тома, не запускайте `docker compose down -v` и не сбрасывайте Docker Desktop ради обычного обновления.

## 11. Обновляйте из приватного GitHub

Сначала проверьте собственные изменения и создайте копию:

```powershell
Set-Location 'C:\QStudy'
git status --short
.\Manage-QStudy-Internet.cmd backup
git pull --ff-only origin main
.\Manage-QStudy-Internet.cmd update
```

Если `git status` показывает изменения исходников, сначала сохраните и согласуйте их. Не используйте принудительный сброс для обхода конфликта. `update` собирает полученный код, сохраняет постоянные данные и повторяет публичную проверку; получение кода из Git само по себе сайт не обновляет. При работающем backend менеджер также создаёт копию перед обновлением.

Другу для обновлений достаточно чтения репозитория. Настоящие настройки домена, почты и ключи не нужно коммитить. Если вместо Git был передан архив, для регулярных обновлений настройте доступ чтения или получайте новые архивы исходников без замены `deployment/.env` и `deployment/data/`.

## Если что-то не работает

| Симптом | Что проверить |
| --- | --- |
| Docker есть, но нет Server | Запущен ли Docker Desktop, Linux Engine, WSL/виртуализация, требуемая перезагрузка |
| Нет доступа извне | Реальный публичный WAN, TCP 80/443 у провайдера, проброс на закреплённый LAN-IP, активный профиль firewall |
| DNS указывает не туда | `A`, смена динамического IP, DDNS/VPN; лишняя неподготовленная `AAAA` |
| Caddy не получил сертификат | DNS и входящие 80/443, конфликт с другим веб-сервером; не удалять сертификаты при каждой попытке |
| Главная работает, запись или вход дают 403 | Точный HTTPS-домен в `PUBLIC_BASE_URL`, отсутствие обходного доступа к frontend |
| База пустая | Исходники не содержат базу; восстановить штатный ZIP и проверить исходное имя архива |
| Письмо содержит localhost | Исправить production `PUBLIC_BASE_URL`, применить `start`, запросить новую ссылку |
| После перезагрузки сайт недоступен | Вход Windows, запуск Docker Desktop, задача QStudy и настройки сна |
| ИИ не отвечает | Ключ, доступная модель, квота и исходящий интернет; отсутствие ключа не компенсируется локальным запуском |
