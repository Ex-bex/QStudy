# QStudy на домашнем компьютере: доступ из интернета

Для выбранного запуска **без домена и сертификата, по `http://БЕЛЫЙ_IP:8080`**, дважды нажмите **`Start-QStudy-Internet.cmd`** на Windows-хосте. Команды, IP и порт для обычного запуска вводить не нужно: кнопка определяет адрес, запускает установленный Docker и при необходимости показывает точное правило ручного проброса с подтверждением в том же окне. [Инструкция для друга](friend-hosting.md). Дальше в этом документе описана дополнительная схема с HTTPS и доменом.

Новый компьютер может стать постоянным хостом QStudy. Арендовать VPS для этого не обязательно. Прямая схема: **пользователь → ваш домашний маршрутизатор → Caddy с HTTPS → QStudy в Docker**. Cloudflare и сторонний туннель в этой схеме не используются. Исходники GitHub остаются закрытыми, а студентам открывается только работающий сайт.

Нужны постоянно включённый компьютер, доступный извне адрес провайдера и настройка роутера. Скрипт на компьютере не может самостоятельно выдать публичный адрес, изменить договор провайдера или настроить роутер без доступа к его панели. После подготовки приложения эти действия владелец выполняет один раз. Пока они не выполнены и проверка с другой сети не прошла, действительного публичного сайта ещё нет.

Для отдельного варианта с собственным доменом используйте HTTPS-настройку этого документа и [инструкцию развёртывания](deployment.md). Команда `prepare` собирает приложение и запускает только внутренние backend/frontend без открытых портов. После неё можно создать администратора либо выполнить `restore -Archive ИМЯ.zip -NoPublish`, а уже затем настроить сеть и выполнить `start`.

В примерах `my-qstudy.duckdns.org`, `owner@example.org`, `192.168.1.50` и названия резервных копий вымышлены. Подставьте свои значения. Доступность конкретного доменного имени не проверялась. Все команды `.cmd` запускаются в PowerShell из корня перенесённого проекта, например `C:\QStudy`.

## 1. Проверьте интернет-подключение

Откройте панель вашего роутера и найдите **Internet / WAN / IPv4 address**. Это адрес внешнего интерфейса роутера; не путайте его с адресом компьютера в локальной сети.

Если WAN входит в следующие диапазоны, прямой IPv4-доступ через ваш роутер обычно недоступен:

| Адрес WAN | Значение |
| --- | --- |
| `10.0.0.0–10.255.255.255` | Приватная сеть перед вашим роутером |
| `172.16.0.0–172.31.255.255` | Приватная сеть перед вашим роутером |
| `192.168.0.0–192.168.255.255` | Приватная сеть или второй домашний роутер |
| `100.64.0.0–100.127.255.255` | Общий адрес провайдера, часто CGNAT |

Диапазон CGNAT закреплён в [RFC 6598](https://www.rfc-editor.org/info/rfc6598/). При CGNAT обычный проброс портов на домашнем роутере не создаёт доступ снаружи: требуется публичный адрес у провайдера. [Разъяснение TP-Link](https://www.tp-link.com/ph/support/faq/785/).

Спросите провайдера:

> Нужен публичный IPv4 для домашнего веб-сервера, без CGNAT, с разрешёнными входящими TCP 80 и 443. Можно динамический адрес. Есть ли блокировка этих портов и разрешён ли сервер условиями подключения?

**Публичный и статический — разные свойства.** Публичного динамического IPv4 достаточно вместе с DDNS. Статический адрес удобнее, но для описанной схемы не обязателен; услуга провайдера может быть платной даже без аренды VPS.

Если у вас два собственных роутера, настройте проброс на обоих либо попросите перевести внешний модем в bridge с сохранением необходимых настроек. При CGNAT оборудование провайдера вы таким образом не исправите. [Официальная инструкция по пробросу](https://www.tp-link.com/us/support/faq/1379/).

VPN на хосте может менять наблюдаемый внешний адрес. До первичной проверки DDNS и прямого доступа отключите VPN для хоста либо заранее настройте маршрутизацию так, чтобы сайт и DDNS использовали именно домашнее подключение.

## 2. Подготовьте новый компьютер

Для пути через Windows используйте поддерживаемую 64-битную Windows 11, включённую виртуализацию в BIOS/UEFI, как минимум 8 ГБ оперативной памяти и достаточно места для Docker, образов, загрузок и копий. Официальные требования Docker Desktop включают WSL 2 версии 2.1.5 или новее и 8 ГБ RAM. Для одновременной работы Windows, сборки Next.js и OCR практичнее иметь 16 ГБ; это рекомендация для удобства, а не проверенный предел нагрузки QStudy. [Требования Docker](https://docs.docker.com/desktop/setup/install/windows-install/).

1. Подключите хост к роутеру Ethernet-кабелем, если возможно.
2. Установите обновления Windows и включите виртуализацию, если установщик сообщает, что она выключена.
3. В параметрах питания запретите автоматический сон **при питании от сети**. Экран может выключаться; сам компьютер должен продолжать работать.
4. Подготовьте папку проекта, например `C:\QStudy`. Скачивание только Git-репозитория не переносит текущую базу, документы и рабочие секреты.
5. Храните исходники и данные вне публичных сетевых папок и не передавайте доступ Docker незнакомым пользователям компьютера.

Если новый компьютер предназначен исключительно для сервера, можно установить на него Ubuntu 24.04 LTS и использовать [Linux-инструкцию](deployment.md). Покупать VPS при этом также не требуется: Linux будет работать на вашем оборудовании, а разделы DNS, адреса провайдера и роутера из этой инструкции остаются актуальны. Такой вариант удобнее для запуска после включения питания без входа в рабочий стол.

## 3. Закрепите локальный адрес хоста

В панели роутера найдите **DHCP reservation / Address reservation / Статическая аренда**. Закрепите за сетевой картой нового компьютера свободный адрес в вашей сети, например `192.168.1.50`.

Узнать текущие настройки в PowerShell:

```powershell
Get-NetIPConfiguration
```

Нужны активный Ethernet/Wi-Fi, его IPv4 и Default Gateway. Виртуальные адаптеры Docker, WSL и VPN не являются адресом для проброса с роутера. Если адрес компьютера меняется после перезагрузки, правила проброса начнут указывать на другой компьютер — поэтому DHCP reservation важна.

## 4. Получите доменное имя

Бесплатный вариант — [DuckDNS](https://www.duckdns.org/). Это DDNS: сервис связывает имя с вашим изменяющимся публичным IP; HTTP-запросы к QStudy по-прежнему идут прямо на домашний компьютер.

1. Войдите в DuckDNS своим аккаунтом.
2. Создайте свободное имя, например `my-qstudy`, получив `my-qstudy.duckdns.org`.
3. Сохраните токен DuckDNS приватно. Его нельзя размещать в Git, скриншотах или командах, которые публикуются в чат.
4. Настройте автоматическое обновление адреса штатным DDNS-клиентом вашего роутера, если он поддерживает DuckDNS. Используйте HTTPS; в настройках укажите только собственное имя и токен.
5. Если роутер не поддерживает DuckDNS, из папки проекта выполните команды ниже **до первого запуска сайта**. Выберите один основной обновляющий клиент, чтобы разные устройства или VPN не перезаписывали адрес.

```powershell
Set-Location 'C:\QStudy'
.\Manage-QStudy-DuckDNS.cmd configure
.\Manage-QStudy-DuckDNS.cmd update
```

Введите короткое имя `my-qstudy`, затем токен в скрытом запросе. Состояние и регулярное обновление описаны в разделе «Обновление DuckDNS» ниже. Клиент DuckDNS не требует Docker, Node.js или Python.

Можно использовать купленный домен: создайте `A` на ваш публичный IPv4 либо `CNAME` подходящего поддомена на имя DuckDNS. Не добавляйте `AAAA`, если входящий IPv6 не настроен и не проверен. [Возможности собственного домена DuckDNS](https://www.duckdns.org/faqs.jsp).

DuckDNS и покупка домена не обходят CGNAT и не открывают порты. Публикация адреса в DNS также означает, что публичный IP домашнего подключения можно узнать по домену.

## 5. Установите среду и подготовьте QStudy

Дальнейшие команды выполняются из папки проекта в PowerShell. Установка включает производственные Linux-контейнеры; Python, Node.js, зависимости QStudy и Tesseract для распознавания PDF находятся в образах и не требуют отдельной ручной установки на Windows.

1. Скачайте [Docker Desktop для Windows](https://docs.docker.com/desktop/setup/install/windows-install/) с официальной страницы и установите его. Если WSL ещё не подготовлен, откройте PowerShell от имени администратора и выполните `wsl --install --no-distribution`, затем `wsl --update`. [Команды WSL](https://learn.microsoft.com/en-us/windows/wsl/basic-commands). Если установка просит перезагрузку, выполните её и войдите в тот же аккаунт Windows.
2. Откройте Docker Desktop, прочитайте и примите условия самостоятельно, выберите Linux containers / WSL 2 и дождитесь запуска Docker Engine. Команды QStudy не принимают лицензионные соглашения вместо владельца.
3. В PowerShell откройте папку проекта и проверьте среду:

```powershell
Set-Location 'C:\QStudy'
docker version
docker compose version
```

В `docker version` должны отображаться и Client, и Server. Если есть только Client и ошибка соединения с Engine, Docker ещё не готов. Сам Docker Desktop и компоненты Windows устанавливаются один раз; библиотеки QStudy дальше автоматически устанавливаются при сборке контейнеров.

Менеджер использует только локальный Docker Desktop и отклоняет удалённые `DOCKER_HOST` или Docker-контексты. Если раньше вы управляли другим сервером через Docker, выберите локальный контекст Linux containers самостоятельно; сохранённые настройки контекстов скрипт не меняет. [Выбор подключения Docker](https://docs.docker.com/reference/cli/docker/).

Создайте публичную конфигурацию:

```powershell
.\Manage-QStudy-Internet.cmd init -Domain 'my-qstudy.duckdns.org' -Email 'owner@example.org'
notepad .\deployment\.env
```

`deployment/.env` — отдельная конфигурация публичного запуска. Она не должна попадать в Git и не заменяет автоматически настройки прежнего `backend/.env`. Секреты создаются случайно; при повторной настройке не меняйте их без необходимости. В редакторе заполните:

| Настройка | Что указать |
| --- | --- |
| `QSTUDY_DOMAIN` | Ваше DNS-имя без `https://` и пути |
| `PUBLIC_BASE_URL` | `https://` и то же имя, без завершающего `/` |
| `ACME_EMAIL` | Ваш email для уведомлений о сертификате |
| `REGISTRATION_ENABLED` | `false` на время первоначальной настройки и переноса |
| `GEMINI_API_KEY` | Рабочий ключ ИИ из ваших настроек |
| `RECOVERY_DELIVERY` | `smtp`, если почта настроена; иначе `disabled` |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURITY`, `SMTP_USERNAME`, `SMTP_PASSWORD`, `SMTP_FROM` | Рабочая почта по [инструкции](mail.md) |

Для текущего Gmail SMTP используется `smtp.gmail.com`, порт `587`, `starttls` и пароль приложения Google. Провайдер и Windows должны разрешать исходящий SMTP 587. `SMTP_FROM` задаёт имя отправителя, например `QStudy <your_email@gmail.com>`; `PUBLIC_BASE_URL` задаёт адрес ссылки восстановления. Домашний хост не требует собственного почтового сервера.

Записывайте значения `.env` в одинарных кавычках по шаблону, особенно пароль с `$`. Не запускайте `.env` как скрипт и не выводите раскрытую конфигурацию `docker compose config`: она содержит секреты.

## 6. Разрешите входящие соединения Windows

Создайте в Windows правило для входящего HTTPS:

1. Нажмите `Win + R`, введите `wf.msc` и откройте **Брандмауэр Защитника Windows с расширенной безопасностью**.
2. Выберите **Правила для входящих подключений → Создать правило → Для порта**.
3. Укажите **TCP**, **Определённые локальные порты**: `80,443`.
4. Выберите **Разрешить подключение** и действующий профиль сети домашнего хоста. Если домашняя сеть доверенная и отмечена «Частная», выбирайте этот профиль.
5. Назовите правило `QStudy HTTP HTTPS` и сохраните.

Для необязательного HTTP/3 можно создать отдельное правило для UDP 443 по той же последовательности. Профиль сети можно проверить командой `Get-NetConnectionProfile`; не меняйте незнакомую сеть на доверенную только ради публикации.

Docker Desktop принимает опубликованные соединения через `com.docker.backend.exe`; антивирус или корпоративный сетевой фильтр тоже должен разрешать эту операцию. Не выключайте брандмауэр целиком. [Сетевой путь Docker Desktop](https://docs.docker.com/desktop/features/networking/).

Порты 3000 и 8000 наружу открывать не нужно: в производственной схеме frontend и backend доступны только внутри сети контейнеров. Не публикуйте Docker API и Windows Remote Desktop вместе с сайтом.

## 7. Настройте проброс на роутере

В **Port Forwarding / NAT Forwarding / Virtual Servers** добавьте:

| Внешний порт | Протокол | Внутренний IP | Внутренний порт |
| --- | --- | --- | --- |
| 80 | TCP | IP закреплённого хоста, например `192.168.1.50` | 80 |
| 443 | TCP | Тот же IP хоста | 443 |
| 443, необязательно | UDP | Тот же IP хоста | 443 |

Внутренний IP — адрес Windows-компьютера, не контейнера и не виртуального адаптера WSL. Не используйте режим DMZ или открытие всех портов. Если панель удалённого управления роутером занимает внешние 80/443, отключите её внешний доступ либо перенесите управление согласно документации роутера.

Для Caddy нужны правильный домен и доступные входящие порты: он получает публичный сертификат и продлевает его автоматически. Описанная конфигурация использует обычные ACME-проверки через 80/443, без DNS-плагина. [Настройка HTTPS Caddy](https://caddyserver.com/docs/quick-starts/https).

Локальный автоматический подбор свободного порта не заменяет этот шаг. В публичном запуске используются стандартные 80/443; если они заняты IIS или другим веб-сервером, сначала определите конфликт и остановите/перенастройте именно мешающий сервис. Не останавливайте неизвестный процесс автоматически.

## 8. Проверьте сеть и запустите сайт

```powershell
.\Test-QStudy-HomeNetwork.cmd -Domain 'my-qstudy.duckdns.org'
.\Manage-QStudy-Internet.cmd check
.\Manage-QStudy-Internet.cmd start
```

В диагностике можно передать `-RouterWanIPv4` с действительным WAN IPv4 из панели роутера; тогда она сравнит его с наблюдаемым внешним адресом и отметит приватный адрес или вероятный CGNAT. Самостоятельного входа в роутер и сканирования других устройств нет. Отчёт сохраняется в исключённом из Git `.local/home-network-report.json`. `-Offline` отключает внешние запросы; такая проверка не подтверждает DNS и внешний адрес.

Диагностика помогает сравнить адреса и найти конфликт портов, но компьютер не может доказать доступность из интернета, проверяя только самого себя. Успешная сборка контейнеров также не доказывает внешний доступ. Менеджер запуска проверяет настроенный HTTPS-домен; если роутер не поддерживает NAT loopback, внутренний тест может завершиться ошибкой при работающем внешнем сайте — поэтому обязательно нужна следующая независимая проверка.

После запуска:

1. На телефоне **выключите Wi-Fi**, оставьте мобильный интернет.
2. Откройте `https://my-qstudy.duckdns.org`.
3. Убедитесь, что нет предупреждения о сертификате и открывается именно QStudy.
4. Проверьте `https://my-qstudy.duckdns.org/api/health`: ожидается успешный ответ с сервисом `QStudy`.
5. После настройки администратора проверьте вход и выход, сохранение заметки, загрузку файла и корректный домен ссылки восстановления пароля.

Только такая проверка подтверждает доступ сайта из другой сети. Ссылку с `127.0.0.1`, `localhost`, `192.168.*` или `10.*` студентам отправлять нельзя: она не обозначает ваш публичный сайт.

Если сайт открывается по мобильному интернету, но не открывается дома по тому же домену, возможна проблема NAT loopback роутера. Настройте NAT loopback или локальное DNS-разрешение **того же домена** на адрес хоста, сохраняя HTTPS и имя сертификата. Не переключайте публичный вход на HTTP и не отключайте проверку Origin ради этого.

## 9. Перенесите данные или создайте администратора

При переносе используйте готовую резервную копию из прежней админки. Она содержит согласованную базу и загруженные файлы. Перенос только Git-репозитория создаёт новую установку без действующих аккаунтов и учебных материалов.

1. На прежнем компьютере создайте и скачайте штатный ZIP резервной копии. Сохраните отдельно рабочий `.env` в приватном месте.
2. Завершите работу на старом хосте и остановите его, чтобы новые записи не остались только там.
3. Поместите ZIP с исходным именем в `deployment/data/backups/` нового проекта.
4. Проверяйте и восстанавливайте архив штатным менеджером; не распаковывайте SQLite поверх работающей базы.

```powershell
.\Manage-QStudy-Internet.cmd verify -Archive 'qstudy-20261011-120000-abcd1234.zip'
.\Manage-QStudy-Internet.cmd restore -Archive 'qstudy-20261011-120000-abcd1234.zip'
```

При переносе существующий административный аккаунт переносится с базой. Если установка новая, создайте первого администратора:

```powershell
.\Manage-QStudy-Internet.cmd admin -Email 'your-admin@example.org' -Name 'Администратор'
```

Пароль вводится скрыто и повторяется; не передавайте его аргументом командной строки. Для существующего email bootstrap-команда меняет пароль и отзывает прежние сессии — поэтому не запускайте её после восстановления базы без намерения сменить пароль.

После проверки администратора и данных разрешите регистрацию, если она нужна, через `REGISTRATION_ENABLED='true'` в `deployment/.env` и повторите запуск. Для управления аккаунтами, группами, расписанием, силабусами и логотипами используйте [руководство администратора](user-guide.md).

## 10. Настройте повседневную работу

Основные команды:

```powershell
.\Manage-QStudy-Internet.cmd status
.\Manage-QStudy-Internet.cmd backup
.\Manage-QStudy-Internet.cmd mail-check
.\Manage-QStudy-Internet.cmd update
.\Manage-QStudy-Internet.cmd stop
```

`Update` получает новые образы/собирает текущие исходники; получение нового кода из Git выполняйте перед этой командой, сохраняя приватные данные. Производственная сборка не подхватывает изменение исходников мгновенно, как сервер разработки. При обновлении работающего приложения создаётся резервная копия.

Данные сохраняются в `deployment/data/backend/` и `deployment/data/backups/`, сертификаты — в постоянных Docker volumes. Не удаляйте `deployment/data/`, Docker volumes или всю папку проекта ради обновления. Включённые в QStudy автоматические копии хранятся на этом же компьютере; периодически сохраняйте дополнительную копию на другом защищённом носителе. Для проверки восстановления используйте отдельную тестовую установку, не перезаписывая основной сайт.

В Docker Desktop включите **Settings → General → Start Docker Desktop when you sign in to your computer**. У контейнеров задан перезапуск `unless-stopped`: после запуска Docker они возобновляются, кроме контейнеров, которые вы явно остановили. [Настройка Docker Desktop](https://docs.docker.com/desktop/settings-and-maintenance/settings/).

**Ограничение Windows-варианта:** автоматический запуск Docker Desktop при входе не означает запуск после включения компьютера до входа пользователя. После перезагрузки войдите в тот же Windows-аккаунт и проверьте статус сайта. Скрипты не отключают пароль Windows и не настраивают автоматический вход. Для хоста без участия человека после перезагрузки предпочтительнее Ubuntu на этом компьютере с Docker Engine как системной службой.

Для автоматической проверки и запуска QStudy после входа в Windows можно создать штатную задачу:

```powershell
.\Manage-QStudy-Internet.cmd install-autostart
```

Она работает для текущего пользователя при входе в систему. Docker Desktop также должен запускаться при входе. Для отключения задачи выполните `remove-autostart`; это не удаляет данные и не означает автоматическое выключение работающих контейнеров. Если задача включена, следующий вход снова запустит QStudy даже после команды `stop`. Для длительной остановки сначала отключите автозапуск, затем выполните `stop`.

Для DDNS на компьютере настройте регулярное обновление адреса. Оно должно сохраняться после перезагрузки; разовое обновление при запуске недостаточно, если провайдер меняет IP во время работы сайта. Подробности команды DDNS приведены ниже. Падение питания, интернета, сон компьютера или остановка Docker делают сайт недоступным. ИБП полезен, но не заменяет резервную копию.

## Обновление DuckDNS

Клиент на компьютере узнаёт внешний IPv4 по HTTPS через [ipify](https://www.ipify.org/), затем обновляет выбранное имя через [HTTPS API DuckDNS](https://www.duckdns.org/spec.jsp). Токен получает только DuckDNS: он хранится приватно и не выводится в журнал. IPv6 этот клиент не обновляет.

На роутере используйте встроенную поддержку DuckDNS. Если её нет, из корня проекта выполните:

```powershell
.\Manage-QStudy-DuckDNS.cmd configure
.\Manage-QStudy-DuckDNS.cmd update
.\Manage-QStudy-DuckDNS.cmd install-autostart
.\Manage-QStudy-DuckDNS.cmd status
```

`configure` запросит короткое имя, например `my-qstudy`, и затем скрыто токен. Не передавайте токен аргументом командной строки. Он хранится в `.local/secrets/duckdns.json`, защищён DPAPI текущего Windows-пользователя и ограниченными правами. Файл не попадает в Git. Клиент обновляет адрес HTTPS-запросом, не печатая токен или URL с ним.

`install-autostart` создаёт задачу текущего пользователя с обновлением каждые 5 минут. Она не работает от SYSTEM и не получает чужие полномочия. Перед запуском убедитесь, что внешний адрес определяется через домашний интернет, а не VPN. `remove-autostart` отключает регулярное обновление; `status` показывает состояние без токена.

При переносе на другой компьютер настройте токен снова: защита DPAPI привязана к пользователю и компьютеру, поэтому простое копирование файла не переносит рабочие полномочия. Если токен случайно раскрылся, перевыпустите его в своём DuckDNS-аккаунте и повторите `configure`.

## Если прямой доступ невозможен

| Ситуация | Что делать |
| --- | --- |
| Провайдер выдаёт CGNAT | Запросить публичный IPv4. Бесплатный домен и проброс на своём роутере это не исправляют |
| Есть публичный IPv4, но входящие 80/443 заблокированы | Узнать у провайдера возможность их открыть. TCP 443 нужен посетителям; если заблокирован только 80, Caddy может подтвердить сертификат через [TLS-ALPN на 443](https://caddyserver.com/docs/automatic-https#tls-alpn-challenge), но HTTP-переадресация будет недоступна. Здесь предусмотрена обычная настройка обоих портов |
| Доступен только публичный IPv6 | Возможно отдельное размещение по IPv6, с правилом входящего трафика и корректной `AAAA`. Сети без IPv6 такой сайт не откроют; эта инструкция и автообновление DuckDNS рассчитаны на IPv4 |
| Требуется доступ через CGNAT без публичного IP | Нужен внешний посредник с исходящим туннелем, например ngrok, либо другой публичный хост. Это отдельная схема, даже если приложение остаётся дома |

У [ngrok](https://ngrok.com/docs/pricing-limits/free-plan-limits) есть бесплатный домен и исходящий туннель, но тариф вводит ограничения и промежуточную HTML-страницу для посетителей. Для постоянной учебной платформы это требует отдельной оценки тарифа, адреса и корректного проксирования QStudy. Он не установлен и не включён этой инструкцией; готовая прямая схема обходится без него. Ни покупка VPS, ни Cloudflare не являются обязательными, если провайдер предоставляет прямой входящий доступ.

## Частые проблемы

| Симптом | Проверка |
| --- | --- |
| Docker не запускается | Виртуализация BIOS/UEFI, актуальный WSL 2, перезагрузка после установки, запущенный Docker Engine и Linux containers |
| Порт 80 или 443 занят | Определить владельца порта: IIS, другой Caddy/nginx или приложение. Перенастроить конфликтующий сервис; публичные порты не заменяются случайными автоматически |
| DNS указывает на старый IP | Клиент DDNS, токен, отсутствие VPN и совпадение домена с `deployment/.env` |
| Внешний IP не совпадает с WAN роутера | CGNAT, второй роутер или VPN; сверить реальную схему подключения с провайдером |
| Контейнеры работают, с телефона сайт не открывается | Проброс, закреплённый локальный IP, брандмауэр Windows, блокировка провайдера; проверить именно с выключенным Wi-Fi |
| Caddy не получил сертификат | Домен, DNS, ошибочная `AAAA`, доступ входящих 80/443. Сохранять постоянное хранилище сертификатов; не повторять бесконечно удаление volumes |
| Главная открывается, вход возвращает 403 | Один точный HTTPS-домен в `PUBLIC_BASE_URL`, корректный Host через Caddy; не открывать контейнер frontend в обход HTTPS-прокси |
| Ссылка восстановления ведёт на localhost | Исправить `PUBLIC_BASE_URL` в публичном `.env`, применить запуск и запросить новую ссылку |
| После перезагрузки сайт не работает | Войти в Windows, дождаться Docker Desktop, проверить Status и необходимость Start; убедиться, что компьютер не уснул |
| База после переноса пустая | Git не содержит пользовательскую базу; восстановить проверенный ZIP вместе с загрузками |

Полная эксплуатация, резервные копии и структура публичного развёртывания описаны также в [инструкции Linux-хоста](deployment.md), а самостоятельные изменения — в [руководстве настройки](customization.md).
